# Оргструктура и процессы — Кубышка + AI-роли

Кирилл попросил сделать «агентов под каждую роль» и оргструктуру/процессы на
их основе, предложив довериться более оптимальному варианту, если он есть.
Ниже — предложенный вариант и почему он выглядит так.

## Что это НЕ такое

Роли ниже — это **консультационные персоны внутри `team_bot`** (см.
`shared/role_agents.py`), не автономные исполнители. `/techlead` не пишет
код и не мержит PR, `/qa` не гоняет тесты сама. Каждая роль — это точка
зрения поверх контекста проекта (Docs FinAssist/Finik-backend) и
инженерного плейбука Авито (`avito_playbook/`), которую любой человек в
команде может спросить в любой момент, не отвлекая реального тимлида/QA/
дизайнера. Решение и работу всё ещё делают люди (и Claude Code — при
непосредственной разработке).

Рассматривались более амбициозные варианты (агенты, реально выполняющие
работу роли — гоняющие тесты, кликающие Figma, коммитящие код) — отклонены
на этом этапе: для команды такого размера это непропорционально дорого по
интеграциям (CI, дизайн-тулы, реальный код-execution на каждую роль
отдельно) относительно пользы; консультационный слой даёт большую часть
ценности («вторая точка зрения по роли, доступная 24/7») почти бесплатно,
поверх уже существующей инфраструктуры `team_bot` (LLMClient, docs_context).
Если консультационный слой приживётся и будет реально использоваться —
логичный следующий шаг взять 1-2 роли (вероятнее всего QA — чеклисты
тест-кейсов легко довести до реального прогона) и дать им реальные
интеграции.

## Роли

Взяты не все профили из плейбука Авито (там ещё DS/DS-менеджеры/
BI-разработчики/аналитика — рассчитаны на компанию 12000+ человек), а
только пять, реально релевантных маленькой продуктовой команде:

| Роль | Команда | Что подключает из контекста |
|---|---|---|
| Разработчик | `/dev` | `developer-profile.md`, `development-principles.md`, `avito-developer-practice.md` |
| Тимлид | `/techlead` | `techlead-profile.md`, `tech_design_review.md`, `processes-and-standards.md` |
| QA | `/qa` | `QA-profile.md` |
| Дизайнер | `/design` | `design-levels.md`, `design-management.md` |
| Продукт | `/product` | `product-levels.md`, `goal-setting.md` |

Плюс тематическое подключение файлов по ключевым словам вопроса
(`topic_context_files` в `shared/docs_context.py`) — как и для обычного
`/ask`. `/roles` в самом боте даёт эту же справку живьём.

Продуктовые файлы плейбука (профили, `goal-setting.md#performance-review` и
т.п.) — это карьерные лестницы/чеклисты компетенций Авито, не пошаговые
инструкции «как делать работу». Персоны используют их как ориентир уровня
качества/зрелости, а не как буквальный регламент — и явно проинструктированы
не тащить в маленькую команду процессы, рассчитанные на масштаб Авито
(SPT/TMM/Risk Based Testing и т.п. упоминаются только если реально уместны).

## Иерархия

Для команды такого размера (по факту — Кирилл + несколько человек, не
десятки) полноценная иерархия менеджеров избыточна и не строилась.
Единственная структурная связь, которая реально нужна: **тимлид-роль —
финальная инстанция по архитектурным решениям**, остальные роли —
равноправные консультации. Это отражено только в промптах (`/techlead`
явно проверяет консистентность с уже принятыми в проекте решениями), не в
каком-то отдельном коде прав доступа — все команды доступны всем в чате,
как и остальной функционал `team_bot`.

## Процесс: жизненный цикл задачи

Полноценный процесс Авито (SPT/ZBP/ATDD/TDR/LSR) избыточен для команды
этого размера — вместо копирования один-в-один взят его дух и адаптирован
под то, что уже реально работает в `team_bot` (доска задач, статусы
`open`/`testing`/`done`, `/cancel`):

1. **Идея → задача.** `/task <текст>` (или реплаем на сообщение с идеей) —
   задача попадает на доску. Не обязательно проходить `/product` для
   каждой мелочи — эта роль полезна, когда неочевидно, стоит ли задача
   приоритета вообще (`/product стоит ли делать X сейчас?`).
2. **Нетривиальные изменения — мини-TDR.** Перед стартом чего-то с реальным
   архитектурным весом (не для мелких правок) — спросить `/techlead
   <описание подхода>`. Это НЕ формальный процесс с шаблоном и очередью
   (как настоящий TDR в `tech_design_review.md`) — просто разговор с
   ролью перед тем, как тратить время на реализацию в возможно неверном
   направлении. По желанию можно спросить и `/dev` о сложности реализации.
3. **Реализация.** Как обычно — человек (или Claude Code) пишет код.
   `/claim <номер>` — взять задачу себе.
4. **На тестирование.** `/testing <номер>`. Здесь полезно `/qa <фича или
   баг>` — получить чеклист тест-кейсов заранее, а не придумывать сценарии
   на ходу.
5. **UI-изменения — сверка с дизайном.** Если задача трогает экран —
   `/design <что меняется>` перед тем, как считать готовым: не заменяет
   реального дизайн-ревью, но ловит очевидные несостыковки с уже принятыми
   в проекте UI-паттернами.
6. **Готово.** `/done <номер>` (или `/cancel <номер>`, если задачу решили
   не делать — не то же самое, что «сделали»).

Шаги 2, 4, 5 — рекомендация, не гейт: бот физически не может заблокировать
переход задачи между статусами по признаку «а спросили ли роль». Это
осознанный выбор — задачи вроде «поправить опечатку» не должны спотыкаться
о процесс, придуманный для более рискованных изменений.

## Ритм (уже реализовано, без изменений)

- Ежедневный дайджест открытых задач в `TEAM_CHAT_ID` (`reminder_loop`,
  `TEAM_REMINDER_HOUR`).
- Еженедельные итоги спринта по субботам (`sprint_loop`, `TEAM_SPRINT_HOUR`)
  — количественная сводка (`shared/sprint_digest.py`), без затрат на LLM.

Новых фоновых процессов ролевые агенты не добавляют — только
по-требованию команды в чате, чтобы не плодить дополнительные автоматические
сообщения поверх уже существующих дайджестов.

## Стоимость

Ролевые вопросы используют тот же `_rate_limiter` (лимит вопросов в час на
чат), что и `/ask`, — общий бюджетный потолок, не отдельный лимит на
каждую роль (иначе 5 ролей × лимит превратили бы общий бюджетный контроль в
формальность). См. `README.md` → «Экономия токенов» для остального
R-COST-контекста (reasoning_effort=minimal, auto-retry и т.п.) — он общий
для всех вызовов LLM, включая ролевые.
